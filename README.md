# Magenx_ProductAttachments

> **Generated by Claude Code.** This module is a proof of concept for headless
> integration and is published as such.

Per-product files — manuals, spec sheets, care instructions, licence keys —
attached to the sales emails Magento already sends the customer.

Admin-only. There is no storefront surface and no GraphQL: nothing here is
exposed to the Next.js theme, and the customer meets the feature exactly once,
as an attachment on the email they already receive.

## Why this exists

Magento can attach nothing to a transactional email, and since 2.4.7 it is
harder than it looks: mail moved to `symfony/mailer`, and
`Magento\Framework\Mail\MimeMessage` keeps only the **first `TextPart`** it is
handed, silently dropping every attachment part built the documented way. The
extensions that used to work by pushing parts into `TransportBuilder` no longer
can either — its `$messageData` went private.

## How it works

### One place files live

```
pub/media/product_attachments/<sku>/manual.pdf     <- what the product page uploads into
pub/media/product_attachments/<product id>/spec.pdf
```

**Both folders are read, always.** The SKU folder is the one a human recognises
when copying files in over SFTP; the numeric id folder is the stable one,
because a SKU can be edited. There is no attachments table: the filesystem is
the data store, so a `scp` and an admin upload are the same act, and there is
no import step and no second source of truth to desynchronise.

Files whose extension is not in **Allowed Extensions** are ignored — never
listed, never mailed — so `.DS_Store` and half-finished uploads in the folder
cost nothing.

### Product edit page

**Catalog → Products → (a product) → Product Attachments** lists whatever is in
those two folders and uploads into the SKU one. The fieldset appears only while
the feature is enabled for that store view — `enabled` is a master switch, not
an email-only one, so a merchant is never offered an upload whose files would
go nowhere.

- An upload is stored **immediately**, in its final location. A file added to a
  form the admin then abandons stays on disk, visible and deletable next time
  the product is opened.
- Removing a file from the list deletes it **when the product is saved**.
- The uploader needs a saved product: the destination folder is named after the
  SKU, and a new product has neither a SKU nor an id yet.
- Renaming a SKU moves the folder with it.

The save-time sync only ever runs when the form field is actually present in
the product's data. An import, a REST call or a mass attribute update never
carries it, and must not be read as "the admin cleared the list" — that would
empty the catalogue's attachments on the first mass action.

### Email

The files of every product in the order are attached to the sales emails
selected in **Attach To**. Order *comment/update* emails are deliberately never
attached to — they are sent repeatedly over an order's life, and re-sending the
same manuals with each one is how a shop ends up on a spam list.

The hook is `Magenx\ProductAttachments\Model\Mail\AttachmentTransportBuilder`,
wired in `etc/di.xml` as the `transportBuilder` argument of
`Magento\Sales\Model\Order\Email\SenderBuilder` — the class every sales email
passes through, and nothing else does. Newsletter, customer-account and
third-party mail keep the stock builder.

It subclasses `TransportBuilder` and overrides the **protected**
`prepareMessage()`, which is the only seam left: the parent builds precisely the
message it always built, and then the finished Symfony body is wrapped in a
`multipart/mixed` alongside the attachment parts. Rendered HTML, headers,
addresses and subject are untouched, which is what keeps this compatible with
SMTP modules and anything else that rewrites Magento mail. Attachment parts are
Symfony `DataPart`s built directly, because a Magento `MimePart` would be
dropped by `MimeMessage` on the way in.

Attaching is best-effort throughout: a missing, oversize or unreadable file is
skipped and logged to `var/log/magenx_product_attachments.log`, never a reason
for the customer's order confirmation not to be sent.

## Configuration

**Stores → Configuration → Magenx → Product Attachments**

| Path | Default | Notes |
|---|---|---|
| `magenx_product_attachments/general/enabled` | `0` | Master switch. Off: no fieldset on the product form, uploads refused, no email attachments. Files already on disk are left alone |
| `magenx_product_attachments/general/media_directory` | `product_attachments` | Folder under `pub/media`. Global: a per-store value would hide files from the admin looking at another store |
| `magenx_product_attachments/general/attach_to` | `order` | Any of order / invoice / shipment / credit memo |
| `magenx_product_attachments/limits/allowed_extensions` | pdf, doc(x), xls(x), csv, txt, rtf, odt, ods, zip, jpg, jpeg, png, gif, webp | Applies to uploads *and* to files dropped in by hand |
| `magenx_product_attachments/limits/max_file_size` | `10485760` (10 MB) | Per file, enforced on upload and on attach |
| `magenx_product_attachments/limits/max_total_size` | `20971520` (20 MB) | Per email. Files past the budget are skipped, the email still goes |
| `magenx_product_attachments/limits/max_count` | `10` | Per email |

Which sales email is being sent is resolved by comparing the template
identifier against `sales_email/<entity>/template` and
`.../guest_template`, so a **custom template selected in Sales Emails still
gets its attachments** — and an order comment email, which carries the same
`order` template variable as the confirmation, correctly gets none.

## Security

`pub/media` is web-served, so extension handling is not a preference:

- Executable types (`php*`, `phtml`, `phar`, `sh`, `exe`, `js`, `html`, `svg`,
  `xml`, …) are refused whatever is typed into Allowed Extensions. Magento's
  `pub/media/.htaccess` only helps on Apache and only if it was deployed.
- Every path segment is rebuilt from a strict allowlist and stripped of leading
  dots, so a crafted SKU or filename cannot address anything outside the media
  directory.
- The upload controller is gated on `Magento_Catalog::products` — whoever may
  edit the product may attach to it — plus the admin form key, and it re-checks
  the size limit the browser already checked.
- MIME types are read from file content, never from the name the uploader sent.

## Install

```bash
bin/magento module:enable Magenx_ProductAttachments
bin/magento setup:upgrade
bin/magento cache:flush
```

### First-install checklist

- With the feature off, open a saved product → **no** Product Attachments
  fieldset. Turn it on → the fieldset lists whatever is in
  `pub/media/product_attachments/<sku>/`.
- Upload a PDF → it appears under that folder immediately, before saving.
- `scp` a second PDF into the folder → it is listed on the next page load.
- Remove one from the list, save → that file, and only that file, is gone.
- Rename the SKU, save → the folder follows the product.
- Turn the feature on, place an order for that product → the confirmation email
  arrives **with both files and its HTML body intact**. This is the one to check
  first if an SMTP module is installed.
- Place an order for a product with no folder → the email is byte-identical to
  before the module was installed.
- Add an order comment with "Notify Customer" → no attachments on that email.
